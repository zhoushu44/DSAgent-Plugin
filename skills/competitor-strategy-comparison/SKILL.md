# 竞品策略对比分析

使用 DeepSeek Agent 当前智能体已绑定的 `sycm` 店铺会话，在后台请求 DMP 接口。Cookie 保留在 DeepSeekConnect Gateway，不读取、输出或持久化凭证。

## 前置条件

- 用户提供了本店商品 ID 与同叶子类目竞品 ID，以及分析周期（三项必填，缺一先问）。
- 竞品与本店商品属**同一叶子类目**；类目不一致时必须先确认，否则指标不可比。
- 需绑定 sycm（生意参谋/达摩盘）账号；未绑定时引导到账号连接，不猜测数据。

## 工作流

1. **收集输入**：本店商品 ID、竞品 ID（多个）、分析周期；类目不一致先确认。
2. **取数**：调用达摩盘竞品对比接口，拉取整体/流量/人群画像三维数据。
3. **口径核对**：核对周期、层级、指标定义一致；不一致先对齐再比较（参照 evidence-rules 第 4 条）。
4. **三维对比**：经营指标（规模/效率）、流量结构（来源/关键词）、人群画像（职业/消费层级/品牌偏好）。
5. **输出结论**：差异点 → 归因假设（标 Proxy）→ 可执行的调整建议；每条结论带证据分级标注。
6. **报告**：生成 HTML 对比报告，生成前须用户确认。

## 错误处理

- 竞品 ID 查不到：明确说明并请用户核对，不得用相似商品替代。
- 人群画像数据缺失：该维度标 `[unknown]`，只输出经营与流量对比。
- 周期/口径不一致：以较短周期对齐或标注不可比，不得直接拼表。
- 单一数据源结论：涉及"竞品为什么比我好"的归因，必须有 ≥2 个信号印证，否则只列差异不下结论。

## 运行环境

```bash
# cwd 必须位于当前 DeepSeek Agent workspace 或本技能目录
cd "{workspace}/skills/competitor-strategy-comparison"
python -m competitor_strategy_comparison <子命令> ...
```

- 依赖当前 DeepSeek Agent workspace 的 `.dsagent/runtime` 和平台连接 `sycm`。
- stdout 只输出 UTF-8 JSON；数据与业务 Markdown 统一写入 `{workspace}/artifacts/`。
- Cookie、Token 与 CSRF 由 DeepSeekConnect Gateway 携带，不写入技能文件或命令行。
- Windows 环境已统一 stdout/stderr 为 UTF-8，不要使用会改写编码的重定向方式保存 JSON。

## 默认交互方式

用户直接用自然语言描述需求即可，例如“用本店商品 123 对比竞品 456，查看最近 30 天”。从用户描述中提取本店商品 ID、竞品 ID 和时间周期后直接执行，不要求用户使用固定句式、命令格式或补充“直接给业务结论”“不要展示技术字段”等说明。

时间周期必须由用户明确提供。用户可以说具体起止日期，也可以说“最近 7 天”“最近 30 天”等明确时长；如果完全没有提到分析多久，必须先追问“你想分析哪个时间周期？可以给开始/结束日期，或者说最近 7 天、30 天。”在用户回答前不得运行脚本，不得默认最近 30 天，也不得根据当前日期自行猜测。

“最近 N 天”默认不包含执行当天，结束日期固定为昨天，开始日期为结束日期往前推 `N-1` 天，起止日期均计入周期。例如在 `2026-08-28` 执行“最近 7 天”，必须查询 `2026-08-21` 至 `2026-08-27`。除非用户明确说“包含今天”或直接指定包含当天的起止日期，否则不得把今天传给接口。执行前先将解析出的具体起止日期复述给用户；日期换算清楚时直接执行，无需再次确认。

无论用户是否特别声明，正常结果都必须直接给出业务结论和调整建议，并默认隐藏所有程序字段、接口信息、执行过程与结果文件路径。只有用户明确要求查看技术明细或原始数据时，才补充相应内容。

## 1. 收集三项必填输入

执行前必须已有：

- 本店商品 ID：只用于读取本品信息并确定叶子类目。
- 竞品 ID：用户希望精确查询的商品 ID。
- 时间周期：开始日期和结束日期，格式 `YYYY-MM-DD`；相对周期默认截至昨天，不包含今天。

从自然语言中自动识别这三项；不得要求用户改写成命令或固定模板。缺少任一项时，只追问缺少的业务信息。尤其是时间周期缺失时必须停下来询问，不能用默认值继续执行。不向用户返回“多少个竞品”或竞品候选列表。只有当用户不知道本店商品 ID 并明确要求查询时，才可使用 `list-products` 辅助选择本品。

在用户提供或确认竞品 ID 时，必须用自然语言提醒一次：**竞品必须与所选本店商品属于同一个叶子类目，否则达摩盘无法完成对比查询。** 如果用户已经明确说明两者同类目，不重复追问，直接执行后台校验。

## 2. 查询竞品对比数据

取得本店商品 ID、用户输入的竞品 ID 和用户确认的时间周期后才能执行：

```bash
python -m competitor_strategy_comparison analyze \
  --item-id <本店商品ID> \
  --competitor-id <竞品商品ID> \
  --start-date <YYYY-MM-DD> \
  --end-date <YYYY-MM-DD>
```

脚本必须先获取本品叶子类目，再用竞品 ID 校验同类目商品。默认且始终放开全部竞品筛选：不传生命周期、商家层级、GMV 排名、成交水位、价格带等限制项，也不使用任何固定筛选组合兜底。先检查该本品已经设置的成功品，因为已选成功品可能不再出现在弹窗搜索结果中；未命中时再执行无筛选的精确 ID 搜索。不得传空字符串筛选参数。只有返回 `itemId` 与输入竞品 ID 完全一致时才继续；未命中时向用户说明“该竞品可能与本品不属于同一叶子类目，或不在该类目的达摩盘可对比商品池中，请核对类目后重新提供竞品 ID”，不换用相似商品。

### 原子子命令

完整分析默认使用 `analyze`。排查或只取某一模块时，可使用与参考技能一致的原子命令：

| 子命令 | 作用 | 是否写完整分析产物 |
|---|---|---|
| `overall` | 核心经营指标 | 否 |
| `flow` | 推广渠道、计划与关键词 | 否 |
| `audience` | 人群经营对比 | 否 |
| `analyze` | 合并三类数据并写 JSON + 业务 Markdown | 是 |
| `report` | 从内部 JSON 读取 AI 洞察并生成 HTML 报告 | 是 |
| `history` | 查看 workspace 已生成产物 | 否 |

原子命令与 `analyze` 使用同一套本品、竞品和周期参数，也必须先完成同叶子类目精确校验。

## 3. 输出用户看得懂的对比结果

取数命令的 stdout 为 JSON，其中 `artifact_path` 是内部完整数据，`report_path` 是业务版 Markdown。先读取 `report_path` 完成分析，不要为解析 JSON 创建临时 Python/脚本，也不要执行临时文件清理命令。业务版 Markdown 已将核心经营指标、人群、推广渠道、投放计划和关键词分别表格化，分析时不能省略已经取得的数据。

### 完整 HTML 报告工作流

1. 运行 `analyze` 拉取数据并保存 JSON + 业务 Markdown。
2. 读取 `report_path`，按 [references/insights_template.md](references/insights_template.md) 将 AI 分析写入固定路径 `{workspace}/artifacts/竞品策略洞察.md`。
3. 运行 `report --input <artifact_path>` 生成 HTML。

```bash
python -m competitor_strategy_comparison report --input artifacts/dmp_competitor_strategy_<本品>_<竞品>_<结束日期>.json
```

- 成功时 JSON 含 `html_path`；stderr 尾行 `[OUTPUT_FILES] HTML: ...`
- 若缺 AI 洞察文件或章节，JSON 会返回 `insights_pending` 与需补写的路径提示

### HTML 报告结构（对齐参考样例布局）

报告由脚本统一渲染，内嵌 CSS。**布局**对齐参考样例（章节结构、KPI 卡片、渠道分块等）；**配色**沿用蓝白渐变风格：本品蓝色 `#2563eb`、竞品橙色 `#ea580c`、正向差异绿色、负向差异红色。

HTML 固定包含以下九个章节：

1. **对比对象与周期**：本品/竞品对象卡片 + 周期说明
2. **经营结论**：带标签的菱形列表（来自 AI 洞察）
3. **核心经营数据**：4 列 KPI 卡片 + 对比表
4. **流量与成交诊断**：维度解读表 + 诊断框
5. **人群经营数据与诊断**：双行表头人群对比表 + 人群诊断
6. **推广渠道数据与诊断**：渠道总览 + 分渠道卡片（概览/双方方案/渠道判断）
7. **投放计划明细**：汇总表 + 双方已开启计划列表
8. **双方 TOP 关键词**：左右分栏关键词表 + 关键词诊断
9. **调整建议**：带序号圆标与优先级标签的建议卡片

推广场景和投放方案不得全部混在一张总表中。必须先按一级推广渠道分组，例如“关键词推广”“人群推广”“货品全站推”分别使用独立区块；页面返回的其他有数据渠道也各自单独展示。每个渠道区块依次包含：

1. **渠道概览对比**：用同一张短表横向展示本品与竞品的消耗、消耗占比、点击率、点击成本、直接成交金额和直接 ROI。
2. **本品投放方案**：单独表格列出本品在该渠道实际返回的所有方案及展现、点击、点击率、消耗、点击成本、直接成交金额和 ROI。
3. **竞品投放方案**：使用与本品完全相同的列，单独表格列出竞品所有方案，便于逐项对照。
4. **渠道判断**：写入 `## 推广渠道诊断` 章节，说明双方在该渠道的覆盖、投入结构和效率差异。

桌面端可以把“本品投放方案”和“竞品投放方案”并排展示，窄屏时上下排列。某一侧没有返回方案时，只在对应位置说明“本周期未返回可确认的投放方案”，不能省掉整个渠道，也不能写成“未投放”。不要把多个渠道的方案拼成超宽表格或在单元格里堆叠全部指标。

最终回复只提供 3–5 条核心摘要和生成的 HTML 报告，不附内部 JSON、业务 Markdown 或程序字段。HTML 是用户正式交付物；不得用一段聊天长文代替报告。不要自动打开 DMP 页面；如运行环境支持本地报告预览，可以只打开生成的本地 HTML。

基于 Markdown 中的三类业务数据完成分析：

- `key_metrics`：浏览量、付费点击量、免费点击量、成交订单数、支付转化率、单价、成交金额、加购率。其中成交金额按“成交订单数 × 单价”计算。
- `audience_comparison`：人群类型及双方规模、占比、转化差异。
- `promotion_strategy`：一级推广场景的消耗分布，以及“场景投放策略明细”中所有有数据场景的二级投放方案、ROI、CTR、CPC 和同行关键词。

推广策略不能只看一级概览。关键词推广、人群推广、货品全站推必须强制逐个查询；同时遍历页面一级概览返回的其他全部场景 ID，逐个读取“场景投放策略明细”。只判断用户所选周期内是否有投放，并汇总该周期的渠道、计划与累计效果；不读取、不展示逐日趋势或投放天数。页面七类场景中只要本品或竞品任一侧有数据，就必须纳入分析。二级方案必须区分本品值与竞品值，并明确汇总竞品实际开启了哪些计划。TOP 关键词必须分别展示本品和竞品返回的关键词、词类型、展现、点击、点击率和转化率；接口返回空时只能说“本周期未返回可确认的TOP关键词”。接口未返回计划数据时只能说“本周期未返回可确认的计划”，不得写成“竞品未投放”。

每次分析都必须在开头复述本品 ID、竞品 ID、起止日期和自然日天数，确保对象与周期没有串线。所有推广结论严格限定于本次选择的周期：短周期无数据不能外推为历史未投放，也不能用另一个商品、竞品或周期的页面结果证明当前结果缺失。用户要求比较两个周期时，必须分别运行两个周期，再比较渠道占比、计划和关键词的变化。

先完整展示双方数据和差值，再解释可能的策略含义。DMP 对竞品数据做区间化/模糊化时，保留原区间，不取中点冒充精确值。某模块失败时，保留其他成功模块并明确缺失原因；核心数据不足时输出限制，不编造结论。

关键指标必须使用业务名称输出，不直接展示 DMP 原字段名：`IPV` 显示为“浏览量”，`营销推广点击量`显示为“付费点击量”，`自然点击量`显示为“免费点击量”，`成交笔数`显示为“成交订单数”，`笔单价`显示为“单价”。新增“成交金额”，本品和竞品分别按各自的“成交订单数 × 单价”计算；任一乘数缺失或不是可计算的精确数值时显示为“本周期无法计算”，不得用模糊区间中点估算。

正常回复按电商运营决策顺序输出：

1. **对比对象与周期**：本品、竞品、起止日期和自然日天数。
2. **经营结论**：用 3–5 条短句说明当前最主要的经营差距，并明确问题更偏向流量规模、流量结构、转化效率、单价、人群承接还是投放效率。
3. **核心经营数据表**：完整展示浏览量、付费点击量、免费点击量、成交订单数、支付转化率、单价、成交金额和加购率，保留本品、竞品与差异三列。
4. **流量与成交诊断**：从流量规模、付费与免费流量结构、支付转化率、成交订单数、单价和成交金额的关系解释差距。不得仅凭相关性断言因果。
5. **人群经营数据表与诊断**：完整展示所有返回人群的双方人数、成交订单数、支付转化率和收藏加购率；识别应守住的高转化人群、需要扩量的人群和承接偏弱的人群。
6. **推广渠道数据表与诊断**：完整展示所有有数据场景的双方消耗、消耗占比、点击率和直接ROI；判断双方更偏重哪种获客方式，以及本品是覆盖不足、成本偏高还是成交效率偏弱。
7. **投放计划明细表**：展示所有有数据场景下的计划名称及双方累计效果，并单独汇总本品和竞品实际开启的计划，不得只列竞品渠道名称。
8. **TOP关键词数据表与诊断**：本品和竞品分表展示所有返回关键词、词类型、展现、点击、点击率和转化率；指出可补充的流量词、可强化的成交词和高点击低转化风险词。
9. **调整建议**：给出 3–5 条按优先级排序的动作。每条必须写明“数据依据、具体动作、后续观察指标”，避免只写“加大投放”“优化人群”等空泛建议。

表格中只放数据和必要差异，不在单个单元格里堆砌长段分析。表格后的文字负责解释业务含义。已返回的数据行必须完整呈现；没有返回的模块用一句业务限制说明，不创建全是空值的大表。

### 隐藏技术细节

用户正常回复中不要出现以下内容：

- API 路径、请求参数、`datasetId`、`fieldId` 或场景编号。
- `schema`、`status`、`module_errors`、`artifact_path`、`shop_key`。
- `key_metrics`、`audience_comparison`、`promotion_strategy` 等内部字段名。
- “模块成功”、“接口命中”、“返回结构”等技术语句。
- 结果文件的本地路径，除非用户明确要求查看原始数据。

这些字段只用于脚本运行、数据校验和故障排查。如有数据缺失，用业务语言说明“该部分数据本次未取得”及原因，不向用户倾倒程序错误字段。

## 边界

- 不打开、导航或展示 DMP 页面。
- 不将竞品搜索结果做成候选列表；只验证和返回用户指定的竞品。
- 不调用 `/api/goods/grow/define/success` 修改用户的成功品配置。
- 不调用 DMP AI workflow；分析只使用本技能取得的证据。
- 不接受 Cookie、Token 或 CSRF 作为命令行参数。
- 不将“无数据”解释为“竞品没有投放”。

## 证据分级（输出结论前必读）

本技能输出任何"结论"前，先按**证据四分级**标注级别（Observed 直采 / Calculated 计算 /
Proxy 代理推断 / Unknown 未知），并遵守五条禁止推断——尤其是：
**sycm/万相台指数一律标 Proxy，不得当绝对量**；**Unknown 不得当 0 参与平均**。

完整分级表、五条禁止推断与国内场景注释见 [references/evidence-rules.md](references/evidence-rules.md)。
