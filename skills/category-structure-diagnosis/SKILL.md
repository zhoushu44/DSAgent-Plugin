# 类目结构诊断

> 由参谋长平台分析包「类目结构诊断」（playbook v1.2.0）转换而来的技能：
> 原「数据准备 / 引用知识 / AI 分析 / 报告」四类节点分别对应本文 §1 / §2 / §3 / §4。

## 产出

| 产物 | 说明 |
|---|---|
| 类目经营状态 | 各类目的规模、效率、质量、周期内趋势与经营角色（重点 / 机会 / 风险 / 待观察） |
| 全店结构判断 | 核心依赖、第二梯队、无效分散、重叠与资源错配情况 |
| 重点类目下钻 | 最多 5 个重点类目：主要贡献链接、头部依赖、商品梯队、低效冗余 |
| 问题与优先级 | 最重要的类目经营问题、优先级、关键证据与经营影响 |
| 待验证清单 | 需进入单品 / 推广 / 退款专项诊断的对象、`missing_evidence` 与待验证问题 |
| 报告 | HTML「类目结构诊断报告」，生成前需人工确认 |

## 1. 数据准备（取数清单）

### 类目经营汇总表（必需 · 周期总览 + 每日趋势）

用途：以类目级权威汇总完成全店类目比较、角色判断、结构健康与趋势识别。

| 数据集 | 字段 |
|---|---|
| sycm.shop_cate | subCateId 类目 ID、cateName 类目名称、parentCateId 父类目 ID、cateLevel 层级 |
| sycm.item_top | payAmt 支付金额、sucRefundAmt 成功退款金额、payItmCnt 支付件数、payByrCnt 支付买家数、payRate 支付转化率、newPayByrCnt 新支付买家数、payOldByrCnt 老客支付买家数、olderPayAmt 老客支付金额、itemCartByrCnt 加购人数、itemCartCnt 加购件数、itmUv 商品访客、itmPv 商品浏览量、itmStayTime 平均停留时长、itmBounceRate 跳失率、uvAvgValue 访客平均价值 |
| sycm.alimama_item_promotion | alipayInshopAmt 成交金额、charge 花费、roi 投产比、cvr 点击转化率、alipayInshopNum 成交笔数、ctr 点击率、click 点击、adPv 展现 |

### 类目商品链接分析表（必需 · 下钻专用 · 周期总览）

用途：仅用于对类目汇总识别出的重点、机会或风险类目进行商品链接下钻，**不承担全店类目汇总计算**。

| 数据集 | 字段 |
|---|---|
| sycm.item_top | item_id 商品 ID、item_title 商品标题、payAmt、sucRefundAmt、payItmCnt、payByrCnt、payRate、payOldByrCnt、olderPayAmt、itemCartByrCnt、itemCartCnt、itmUv、itmPv、itmStayTime、itmBounceRate |
| sycm.shop_cate | subCateId 类目 ID、cateName 类目名称、cateLevel 层级 |
| sycm.alimama_item_promotion | roi、cvr、alipayInshopNum、alipayInshopCost 成交成本、cartInshopNum 加购数、cartDirNum 直接加购、cartCost 加购成本、wwNum 旺旺咨询数、adPv、ctr、click、ecpc 平均点击花费、charge、ecpm 千次展现花费 |

### 取数规则

- 全店类目比较、贡献、集中度和角色判断**只能以「类目经营汇总表」为主事实源**；不得由商品明细手工汇总后替代权威类目汇总。
- 「类目商品链接分析表」仅用于汇总阶段选出的最多 5 个类目；不得整表载入上下文，也不得分段读全表来重算类目汇总；无法按选定类目安全筛选时，记录下钻限制并停止该项，不扩大读取范围。
- 变化判断用「每日趋势」并检查连续性；只有周期总览或日期不足时，只描述当前状态。
- 缺失、未知、未采集都不等于 0。

## 3. AI 分析要求

**分析目标**：用类目汇总识别重点、机会、风险与结构问题，并对最多 5 个重点类目进行商品链接下钻。

### 判断顺序

1. 先使用「类目经营汇总表-周期总览」校准经营类目体系和可比较层级；全店类目比较、贡献、集中度和角色判断只能以该汇总表为主事实源。
2. 再使用「类目经营汇总表-每日趋势」判断变化的连续性与波动；没有足够连续日期时只描述当前状态，不制造增长或下降结论。
3. 根据类目汇总结果最多选择 5 个重点、机会或风险类目，再使用「类目商品链接分析表」下钻其主要贡献链接、头部依赖和低效冗余。
4. 不得把「类目商品链接分析表」完整载入上下文，不得通过全表分段读取来重新计算类目汇总；若无法按选定类目安全筛选，记录下钻限制并停止该项，不扩大读取范围。
5. 不得为补算上游事实额外取数或执行脚本 / SQL 重算平台指标；只消费本次已交付的数据，筛选和切片在已交付表内完成。字段、场景或粒度超出已交付范围时另做补充取数并标注来源；脚本只允许对已取回的表做摘要。
6. 对每个分析问题对照已引用的知识，区分数据事实、方法判断、知识解释与待验证假设，并为计算结果保留口径记录（calculation_trace）。
7. 最后按经营影响和证据确定性给出优先级，以及需要继续进入单品、推广或退款专项诊断的对象。

### 必须回答的问题

- 当前各可比较类目的规模、效率、质量和周期内趋势分别怎样，哪些属于重点、机会、风险或待观察类目？
- 各类目当前主要承担什么经营角色，角色是否有足够的类目级证据支持？
- 店铺整体类目结构是否存在核心依赖、第二梯队不足、无效分散、重叠或资源错配？
- 最多 5 个重点、机会或风险类目的经营结果由哪些商品链接支撑，是否存在头部依赖、腰部断层或低效冗余？
- 基于当前已交付的链接数量、成交、流量、转化、退款和推广证据，重点类目的商品梯队与供给承接是否存在明确风险？
- 哪些类目或链接需要继续进入单品、推广或退款专项诊断，哪些问题因利润、库存、行业或其他证据不足暂时无法确认？

### 证据要求

- 类目比较必须使用「类目经营汇总表」中同一类目体系、同一层级、同一周期的数据；重复归属、拆并或口径变化必须先说明。
- 类目规模、效率、质量、角色与结构判断必须引用类目汇总证据，不能从商品明细手工汇总后替代权威类目汇总。
- 增长、下降、改善或恶化必须引用每日趋势并检查连续性；只有周期总览或日期不足时只能判断当前状态。
- 集中、断层、分散或资源错配必须引用多个类目的结构证据，不能根据单个类目孤立判断。
- 商品链接下钻仅限汇总阶段选出的最多 5 个类目；头部依赖和低效冗余必须引用筛选后的链接级证据。
- 利润、库存、行业机会、复购、连带、具体根因或价格带判断只有在对应字段存在时才能确认；缺失时必须记录 `missing_evidence`。

### 期望输出

- 各类目的经营状态、周期内趋势和主要角色，识别重点、机会、风险与待观察类目。
- 全店类目结构判断：核心依赖、第二梯队、分散、重叠和资源错配情况。
- 最多 5 个重点类目的主要贡献链接、头部依赖、商品梯队和低效冗余情况。
- 当前最重要的类目经营问题、优先级、关键证据和经营影响。
- 应继续进入单品、推广或退款专项诊断的类目与链接，以及 `missing_evidence` 和待验证问题。

## 4. 报告

- 标题：**类目结构诊断报告**
- 格式：HTML；原包未固定大纲，由 AI 自由设计，建议至少覆盖：
  1. 类目经营状态与角色总览
  2. 全店类目结构问题（核心依赖 / 第二梯队 / 分散 / 重叠 / 资源错配）
  3. 重点类目商品链接下钻（≤5 个）
  4. 问题优先级与经营影响
  5. 后续专项下钻与 `missing_evidence`
- 输出契约：
  - 必须覆盖所有 finding、evidence、knowledge_basis 和 recommendation，结论必须附带证据与行动建议。
  - 运行 ID、步骤 ID、方法 ID、节点 ID、finding / evidence / recommendation 等内部追踪 ID 只保留在 `data-*` 属性中，不进正文。
  - 类目 ID、商品 ID 等业务标识按上游结果正常展示；上游已返回名称时，每次出现业务 ID 都必须同时展示对应名称。
  - 报告需**人工确认后**再定稿。

---

## 5. 禁止与边界

- 不得从商品明细手工汇总替代权威类目汇总，也不得整表读取下钻表来重算类目结构。
- 不得根据单个类目孤立判断整体结构问题。
- 不得把行业经验、类目经验或平台常识描述为当前店铺已发生的事实。
- 利润、库存、行业机会、复购、连带、价格带等超出已交付字段的判断一律进入 `missing_evidence`，不得猜测。
- 本技能只到类目结构层；具体商品根因（流量 / 转化 / 退款 / 推广）应转入对应专项诊断。
