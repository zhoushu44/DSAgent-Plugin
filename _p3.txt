# 03 · 多平台适配层与字段映射：同一份引擎如何落到十个平台

> 分析对象：Chrome MV3 扩展「觅千手 v5.61」（`src-mirror/manifest.json:4` 的 version 字段）。
> 证据源：只读副本 `src-mirror/` 与从 CDN 落盘的 `scripts/_gm.js`（`dist2/goods_manager/js/index.js` 的副本，单行压缩，5,832,042 字符）。
> 坐标约定：明文文件用 `文件:行号`；单行压缩产物用 `文件@字符偏移`（`String#indexOf` 的结果）。
> 本篇只回答一个问题：**「一套扩展、十个平台」在代码里靠哪几层抽象撑住，每一层把平台差异压缩成了什么。**

## 1. 结论先行：适配被切成四层，每层只解决一件事

平台差异不是被「写十份代码」消化的，而是被拆到四个互不重叠的层次里。每一层都有自己的判定依据，上层不知道下层的存在：

| 层 | 判定依据 | 决定什么 | 典型坐标 |
| --- | --- | --- | --- |
| L1 模块层（扩展侧） | 远端模块表的 `patterns`（URL 子串） | 这个 URL 要不要加载 `goods_manager` 引擎 | `scripts/_remote-config.json:425`、`scripts/_remote-config.json:435` |
| L2 注册表层（引擎侧） | `hosts[]` + `pathIncludes[]` | 当前页面算哪个平台、算不算发布页 | `scripts/_gm.js@392304`、`scripts/_gm.js@393099` |
| L3 取数适配器层 | 平台 id → 一个 async 函数 | 运费模板 / 图片空间 / 尺码模板从哪个接口取 | `scripts/_gm.js@411267` |
| L4 字段填充层 | 采集到的商品对象 → 目标请求体 | 图片、SKU 价格、运费、拼多多专有字段怎么塞 | `scripts/_gm.js@912763`、`scripts/_gm.js@913599` |

执行顺序就是 L1 → L2 → L3 → L4：**先把代码送到页面上，再判断「我在哪」，然后去各平台自己的后台接口把元数据捞回来，最后把「采集到的商品」翻译成「目标平台要的请求体」。** 只要某一步判错，后面全错——所以每一层都刻意做得很笨：字符串匹配，不做任何推断。

## 2. L1 模块层：8 个 publisher 指向同一个 `index.js`

远端模块配置里名字带 `_publisher` 后缀的模块共 8 个，它们的 `remoteScripts` 全部是同一行字符串 `dist2/goods_manager/js/index.js@goods_m`：

| 模块名 | `patterns`（URL 子串） | 坐标 |
| --- | --- | --- |
| `goods_manager` | `item.upload.taobao.com`、`sucai.wangpu.taobao.com`、`sell.publish.tmall.com` | `scripts/_remote-config.json:425`、`scripts/_remote-config.json:435` |
| `xiaohongshu_publisher` | `ark.xiaohongshu.com` | `scripts/_remote-config.json:390` |
| `kuai_shou_publisher` | `s.kwaixiaodian.com`、`app.kwaixiaodian.com` | `scripts/_remote-config.json:445` |
| `douyin_publisher` | `fxg.jinritemai.com`、`haohuo.jinritemai.com`、`douyin.com` | `scripts/_remote-config.json:463` |
| `weidian_publisher` | `store.weixin.qq.com`、`weidian.com` | `scripts/_remote-config.json:482` |
| `jd_publisher` | `wares-jdm.jd.com` | `scripts/_remote-config.json:500` |
| `xianyu_publisher` | `goofish.com` | `scripts/_remote-config.json:516`、`scripts/_remote-config.json:524` |
| `1688_publisher` | `offer-new.1688.com`、`work.1688.com` | `scripts/_remote-config.json:532` |

一个容易忽略的细节：**同一份 `index.js` 不只被发布模块加载，还被一批采集模块加载**。`tb_detail`、`1688_detail`、`pdd_sycm`、`pdd_ykd`、`jd_consum`、`dy_detail`、`douyin_detail`、`xhs_detail`、`tb_trade` 的 `remoteScripts` 里同样带着 `dist2/goods_manager/js/index.js@goods_m`。采集侧与发布侧跑的是**同一个包、同一个 `versionKey`（`goods_m`）**，采集端存下的商品对象与发布端读的商品对象因此天然同构——这是「采集完直接上架」不需要额外序列化转换的根本原因。

L1 的匹配算法在 Service Worker 里：`matchModule` 先 `new URL(url)` 取出 hostname，再按模块 `patterns` 逐条做子串包含判断（`src-mirror/script/service_worker_new.js@10553`）。`versionKey` 决定热更缓存键：`dist2/goods_manager/js/index.js@goods_m` 里的 `@goods_m` 就是去远端版本配置取 `goods_m` 版本号的键名。CDN 基址来自 `src-mirror/config/app-config.json:4` 的 `cdnHost`。

**这一层的代价**：8 个 publisher 共享一个 `versionKey`、一份产物，任何一次云端发版都是十平台同时变更，没有灰度、没有按平台回滚。扩展侧也无法审计「今天跑的引擎和昨天是不是同一份」——它只存了一个版本号。

## 3. L2 注册表层：域名 + 路径决定「我在哪、算不算发布页」

代码进了页面之后，引擎必须先回答「这是哪个平台」。它用的是硬编码注册表，两张子表。

**第一张：平台 id → 中文名**（`scripts/_gm.js@392304`，即 `scripts/verify-facts.mjs` 里的 PLAT-01）：

```js
const i={taobao:"淘宝",tmall:"天猫",pinduoduo:"拼多多",douyin:"抖店",
  xiaohongshu:"小红书",1688:"1688",kuaishou:"快手",weidian:"微信小店",
  jd:"京东",xianyu:"闲鱼"};
```

十项，正好对应十个平台。中文名只用于 UI 文案（查不到时回落到「该平台」），不参与任何逻辑分支——文案与判定解耦，改文案不会改行为。

**第二张：平台 id → 域名集合**（`scripts/_gm.js@392510` 起，逐项见 PLAT-02 ~ PLAT-08）：

| 平台 id | `hosts[]` | 备注 | 坐标 |
| --- | --- | --- | --- |
| `taobao` | `sell.taobao.com`、`sell.publish.taobao.com`、`upload.taobao.com`、`item.upload.taobao.com`、`myseller.taobao.com` | 五个子域 | `scripts/_gm.js@392510` |
| `tmall` | `sell.publish.tmall.com`、`myseller.tmall.com`、`sell.taobao.com`… | 与淘宝**共享**部分域名 | `scripts/_gm.js@392638` |
| `pinduoduo` | `mms.pinduoduo.com`、`mobile.yangkeduo.com` | 商家后台 + 移动端 | `scripts/_gm.js@392510` |
| `douyin` | `fxg.jinritemai.com`、`haohuo.jinritemai.com` | 抖店 | `scripts/_gm.js@392638` |
| `jd` | `wares-jdm.jd.com` | 京东商家 | `scripts/_gm.js@392949` |
| `xiaohongshu` | `ark.xiaohongshu.com` | 小红书千帆 | `scripts/_gm.js@392949` |
| `kuaishou` | `s.kwaixiaodian.com` | 快手小店 | `scripts/_gm.js@392949` |
| `weidian` | `store.weixin.qq.com` | 微店实际走**微信小店**域名 | `scripts/_gm.js@393029` |
| `1688` | `offer-new.1688.com`、`member.1688.com`、`work.1688.com` | 三个子域 | `scripts/_gm.js@393029` |
| `xianyu` | `goofish.com` + `pathIncludes:["/publish"]` | **唯一带路径限定的平台** | `scripts/_gm.js@393099`、`scripts/_gm.js@393129` |

闲鱼那一条是整张表里信息量最大的：

```js
xianyu:{hosts:["goofish.com"],pathIncludes:["/publish"]}
```

它解释了一个长期存在的观感差异——闲鱼「采集正常、但很多页面不弹上架入口」。`goofish.com` 是裸域，主机匹配会命中所有子域；但 `pathIncludes` 要求 pathname 或 href 里出现 `/publish`，只有发布页才算「在发布上下文」。商品详情页、聊天页、订单页都判不中，入口自然不出现。

**判定算法由三个小函数串起来**：

1. `function a(e,t)`（`scripts/_gm.js@393581`）：主机名后缀匹配。各自转小写、去掉尾部点，再判断相等或 `endsWith("."+域名)`。因此 `goofish.com` 能命中 `www.goofish.com`、`m.goofish.com`，但**不会**命中 `fakegoofish.com`（必须有 `.` 分隔）。
2. `function l(e,t)`（`scripts/_gm.js@393743`）：路径匹配。`pathIncludes` 为空数组时直接返回 `true`（视为无路径约束）；非空时对 pathname 和 href 各做一次 `indexOf`，任一命中即通过。它对 href 也做包含判断，所以查询串里带 `/publish` 也能过——宽松但有意的取舍。
3. `function c(e,t)`（`scripts/_gm.js@394302`）：组合判定。先查注册表拿 `hosts`，遍历用 `a()` 找第一个命中域名，再要求 `l()` 对 `pathIncludes` 返回真；两者都满足才返回 `true`。

**这是与拦截层完全独立的第二张表**。扩展侧还有一张拦截器平台表 `src-mirror/script/interceptor/config.json`，其中 `platforms` 数组当前只列两项：`taobao`（`src-mirror/script/interceptor/config.json:6`，`urlPatterns` 见 `src-mirror/script/interceptor/config.json:9`）与 `tmall_publish`（`src-mirror/script/interceptor/config.json:51`，`urlPatterns` 见 `src-mirror/script/interceptor/config.json:54`）。那张表决定「抓哪些接口」，这张表决定「在哪儿上架」。两张表确实不一致：拦截层是「抓证据」的子集，引擎侧才是全平台覆盖。

## 4. L3 取数适配器层：元数据每家接口都不一样，用一张分派表兜住

平台判定完成之后，引擎需要三类「平台自己的元数据」：运费模板、图片空间目录、尺码模板。这三类只能从各平台自己的商家后台接口取，路径、鉴权、返回结构都不一样。引擎的处理办法是一张对象分派表（`scripts/_gm.js@411267`）：

| 平台 | 取数实现 | 特殊点 |
| --- | --- | --- |
| `taobao` | `Promise.all([运费, 图片空间, 尺码])` 三路并发 | 三份元数据齐全 |
| `tmall` | 同淘宝，但尺码模板走另一组接口 | 与淘宝代码几乎对称 |
| `pinduoduo` | 运费 + 图片空间两路 | 无尺码模板 |
| `jd` | 运费 + 图片空间两路 | 无尺码模板 |
| `douyin` | 运费 + 尺码模板 | 回填 `sizeTemplateMap` / `sizeTemplateErrorMsg`（`scripts/_gm.js@411817`） |
| `xiaohongshu` | 运费 + 图片空间 | — |
| `weidian` | 只取运费，图片空间固定返回空数组兜底数组 | 走微信小店接口（`scripts/_gm.js@290601`） |
| `kuaishou` | 只取运费，图片空间固定返回空数组兜底数组 | — |
| `xianyu` | 直接返回空运费列表 + 空图片空间 | 不参与模板取数 |
| `1688` | 直接返回空运费列表 + 空图片空间 | 不参与模板取数 |

闲鱼与 1688 直接返回空数组，是「适配」而不是「缺失」：这两家后台没有可复用的运费模板选择接口，硬取只会失败，所以引擎把「没有模板可选」当作合法状态返回，让 UI 走手动填写分支。这解释了为什么在这两家平台上运费模板下拉框经常是空的却仍能发布。

同一层里还有三张平台专属常量表，用来说明「有些能力只有部分平台有」：

- 异步类目入口表（`scripts/_gm.js@412324`）：只有 `taobao` 与 `tmall` 两个键，分别指向 `item.upload.taobao.com/router/asyncOpt.htm` 与 `sell.publish.tmall.com/router/asyncOpt.htm`。其余平台没有异步类目接口，只能同步拉类目树。
- AI 类目表（`scripts/_gm.js@412448`）：同样只有淘宝/天猫，指向 `/sell/ai/category.htm` 与 `/tmall/ai/category.htm`。
- 能力开关表（`scripts/_gm.js@412719`）：`{taobao:!0,tmall:!0}`——「是否支持某能力」用一张只有两个真值的对象表达，比在每个分支里写平台名比较更好维护。

运费模板的具体取数也因平台而异：微信小店走 `store.weixin.qq.com/shop-faas/mmecnodeproductupload/express/cgi/goods/getFreightTemplate`，并且要先从 cookie 里解出 `biz_magic`（`scripts/_gm.js@194132`、`scripts/_gm.js@289239`）；这是唯一需要自己从 cookie 抠 token 的平台，其余平台靠页面已登录态。

## 5. L4 字段填充层：一次 `transformRequestBody` 里串起四步

真正把「采集到的商品」变成「目标平台请求体」的地方是 `transformRequestBody`（`scripts/_gm.js@912763`）。骨架非常短：记录改写前摘要 → 四个填充步骤 → 记录改写后摘要 → 落 `localStorage` 便于取证。四步调用连写在同一行（`scripts/_gm.js@913211`）：

```
this.fillImageData(e,t),this.fillSkuPriceData(e,t),this.fillShippingConfig(e,t),this.applyPddElecGoodsAttributes(e);
```

### 5.1 `fillImageData`：图片、装修楼层、视频三件套（`scripts/_gm.js@913599`）

| 采集源字段 | 目标字段 | 语义 |
| --- | --- | --- |
| `t.gallery` | `e.gallery` | 主图/详情图数组，整体覆盖 |
| `t.floor_list` | `e.decorationDetail` | 详情页装修楼层 |
| `t.preview_url` | `e.decorationPreview` | 装修预览图 |
| `t.video_upload` | `e.gallery.push({file_id,type:6,video_url,url,width,height})` + `e.carousel_video` | 视频作为 `type:6` 的 gallery 项插入 |

容易被忽略的语义细节：`gallery` 数组用 `type` 区分媒体种类（`1` 主图、`2` 详情图、`6` 视频）。`fillImageData` 在覆盖前会分别统计源与目标的 `type1` / `type2` 数量，这是为了在 trace 里算出 `type1Delta` / `type2Delta`，从而在请求被平台拒绝时能判断是「主图丢了」还是「详情图丢了」。视频只有在 `t.video_upload.check_comment` 等于「通过」（审核通过）时才插入——未过审的视频不会进请求体。

### 5.2 `fillSkuPriceData`：把采集端的 SKU 矩阵翻译成目标端的价格矩阵（`scripts/_gm.js@914335`）

这是四层里最复杂的一层，因为它要处理「规格维度数量不一致」这个真实问题：采集端可能 1 维（颜色），目标端可能 2 维（颜色 × 尺码）。函数开头取三样东西：`sku_sort`（规格顺序）、`sku_key`（规格键 → 取值数组）、`sku_price`（规格键 → 价格数组），三者按下标对齐，缺一不可。

要点：

- 维度数 `n` 超过 2 时直接放弃矩阵构造（代码里 `c=n.length>2`），走另一条降级路径；因为 `price_detail` 只接受最多二维矩阵。
- 拼多多单买规则三件套（`pdd_single_buy_rule_type` / `pdd_single_buy_percent` / `pdd_single_buy_fixed_yuan`）从 `movingConfig` 优先读取、回落商品自身字段——这是「用户在移动配置里改的值优先于采集到的值」这一原则的具体实现。
- 价格矩阵的构造另有稳定化函数 `buildStablePriceDetailForFill`（`scripts/_gm.js@781534`），它处理 `sku_sort` 为空但 `sku_key` 有值的畸形数据：从 `sku_key` 的第一个键反推维度数，并夹到 1 或 2。

### 5.3 `fillShippingConfig`：运费模板、发货时限、两件折扣（`scripts/_gm.js@922380`）

三处细节值得单独说明：

1. **发货时限的枚举归一**：`selectTime` 同时接受 `"today"/"1"/"24h"/"2"` 四种写法映射到 86400 秒，`"48h"/"3"` 映射到 172800 秒（`scripts/_gm.js@922634`）。这是为了兼容不同版本 UI 存下来的历史值——老数据是数字，新数据是字符串。
2. **两件折扣的夹取与放大**：输入是折扣率（5~9.9），输出 `Math.round(10*n)` 变成 50~99 的整数（`scripts/_gm.js@922771`）。若输入非法或越界一律回落 9.9（即 99，等于不打折）。这是静默纠正：用户填了 3 折也不会报错，而是被悄悄改成 9.9 折。
3. **`is_default_template_id=1` 与模板 id 同时写**（`scripts/_gm.js@922449`）：平台接口要求两者成对出现，只写 `cost_template_id` 会被判为「未指定默认模板」。

页面上还有一条 DOM 侧的补偿路径（`scripts/_gm.js@657816`）：如果 `selectTime` 有值但请求体字段没生效，会去 `#shipment_limit_second label` 里按中文文案（「当日」「24小时」「48小时」）找对应单选项并点击。也就是说同一语义有「写字段」与「点 DOM」两条实现，前者优先、后者兜底。

### 5.4 `applyPddElecGoodsAttributes`：平台专属分支

前三步是跨平台通用的（虽然字段名带 `pdd_` 前缀），第四步才是真正的平台专属：把电器类目必填属性（能效等级、3C 认证等）补进请求体。它排在通用链路之后，因为输入依赖前三步已经写好的字段。

## 6. 拼多多：唯一一个「字段映射被单独工程化」的平台

拼多多在引擎里占据的代码量明显超过其他平台，原因是它的编辑接口需要原样改写一个已存在的请求体，而不是从零构造。相关映射逻辑集中在这几处：

| 函数 | 作用 | 坐标 |
| --- | --- | --- |
| `resolveSafePddOutGoodsSn` | 商家编码（`out_goods_sn`）按 `productCode_radio` 三选一策略生成，并做加权长度截断 | `scripts/_gm.js@772198` |
| `getPddStockMode` | 库存模式 1/2（统一库存 vs 按 SKU 库存） | `scripts/_gm.js@718934` |
| `buildStablePriceDetailForFill` | 把畸形 SKU 数据结构稳定化成 1~2 维价格矩阵 | `scripts/_gm.js@781534` |
| `_buildListBody` | 商品列表查询体，固定带 `out_goods_sn_gray_flag:!0` 与 `pre_sale_type`、`shipment_time_type` | `scripts/_gm.js@512625` |

`resolveSafePddOutGoodsSn` 的取值策略最能说明字段映射在真实场景里有多琐碎：`productCode_radio` 为 `"2"` 时用 `goods_id`/`productId`，为 `"3"` 时用 `base_attr` 里的「货号」，否则用商品自身编码；再按 `PDD_OUT_GOODS_SN_MAX_WEIGHTED_LEN` 做加权长度截断（中文算 2、英文算 1），超长时返回 `{truncated:!0}` 让上层决定是否提示用户。为什么是加权长度而不是字符数？因为后端按字节长度校验，中文一个字符两字节，纯按字符数截断会在中文商家编码上被拒。

## 7. 一张总表：十平台的差异到底落在哪几个字段上

把 L2/L3/L4 三层的信息合起来看，平台差异最终收敛到下面这张表（`—` 表示该层对该平台无差异，`✗` 表示该能力不适用）：

| 平台 | 发布域 | 路径限定 | 运费模板 | 图片空间 | 尺码模板 | 异步类目 | AI 类目 | 特殊字段 |

## 8. 边界与风险

- **证据边界**：本篇所有引擎侧坐标都来自落盘的 `scripts/_gm.js`（单行压缩，5,832,042 字符），偏移是 `indexOf` 结果；明文坐标来自 `src-mirror/` 只读副本。两者都能用 `node scripts/verify-facts.mjs` 逐条复验（PLAT-01 ~ PLAT-08 即本篇 L2 层的八条事实）。
- **静态分析边界**：压缩后的变量名（`i`、`n`、`ye`、`be`、`Se`、`xe`）是构建产物名，结论以行为为准而非命名。`weidian_publisher` 的 pattern 里同时有 `store.weixin.qq.com` 与 `weidian.com`，但引擎注册表 `weidian` 只认 `store.weixin.qq.com`——即微店页面会加载引擎，但引擎判定平台时会落到「该平台」兜底分支。这是模块表与注册表不一致留下的真实缺口。
- **时效风险**：引擎走 CDN 热更新（`src-mirror/config/app-config.json:4` 的 `cdnHost`），8 个 publisher 共用同一份产物，本文描述只对应 v5.61 落盘那一刻的包。云端随时可能改字段映射，届时坐标仍在、语义可能已变。
- **合规风险**：注册表与填充层的存在意义是「在第三方商家后台以页面身份提交数据」，绕开平台官方开放接口。本文只做原理还原，不构成可用性建议。
- **未验证项**：十个平台的字段级差异只覆盖到引擎侧代码可见的部分；各平台后端实际校验规则（例如哪些字段组合会被拒）需逐平台实测才能穷举。
