1| # 上架引擎附录：装载调度、落库与上报
2| 
3| 本篇是 `docs/02-publish-engine.md` / `docs/02b-publish-request-chain.md` 的补充附录，只补两块正文没展开的工程细节：**上架引擎这份远端产物是怎么被调度、缓存、版本化地装进页面的**，以及**它跑完之后数据落到哪里、出错往哪报**。坐标写法与前两篇一致：扩展本体是明文多行文件，用 `文件:行号`；`scripts/_gm.js` 是 CDN 上那份单行压缩包，行号恒为 1，因此一律用 `文件@字符偏移`（偏移为 `indexOf` 结果，可用 `node scripts/evidence.mjs` 复验）。
4| 
5| ## 1. 起点只有一个字段：cdnHost
6| 
7| 整个上架引擎的地址只由一行配置决定。`src-mirror/config/app-config.json:4` 是 `cdnHost`，值为 `https://cdn-v3.koudai89.com/v2_build`；`src-mirror/config/app-config.json:5` 是 `apiHost`（`https://p-api.koudai89.com`）；`src-mirror/config/app-config.json:7` 是 `versions: 5.61`。安装包里没有任何一个文件叫 publisher，`manifest.json` 只声明了一个 Service Worker（`src-mirror/manifest.json:17`）。所以上架引擎在磁盘上并不存在，它每次都是从 `cdnHost` 现场拉下来的——这是理解后续所有缓存与版本逻辑的前提。
8| 
9| ## 2. 装载器：ModuleLoaderManager 的四段式调度
10| 
11| 调度主体是 `src-mirror/script/service_worker_new.js@4970` 的 `class ModuleLoaderManager`。构造函数里能直接读出它的全部状态：`configCache` / `configCacheTime` / `configCacheTTL=3e5`（配置缓存 5 分钟）、`codeCache`（`Map`，上限 `codeCacheMaxSize=50`）、`versionConfig`、`coreLibrariesLoaded`（`Set`）、`pageLibsCache`、`loadingModules`、`frameGenerations`、`frameDocumentIds`，并启动 `startCacheCleanup()` 每 10 分钟清一次超过 30 分钟的 `pageLibsCache` 条目。注意 `frameGenerations` / `frameDocumentIds` 这一对：它用 `documentId` 变化检测主框架是否发生了新导航，一旦变化就 `bumpGeneration` 递增一代，并把该 frame 的核心库标记、库缓存、正在加载的模块全部作废。这就是上架页刷新后不会复用上一页旧引擎实例的机制来源。
12| 
13| 四段调度依次是：
14| 
15| 1. **取模块清单**。`src-mirror/script/service_worker_new.js@8735` 是 `async getConfig()`，命中 `configCacheTTL` 且非 `isDeBug` 时直接返回内存缓存；未命中则读 `chrome.storage.local` 的 `modelConfig`，再不行才走网络——URL 在 `src-mirror/script/service_worker_new.js@9091`：`` `${AppConfig.cdnHost}/config.json?v=${e}` ``，`e` 是 `Date.now()`，并挂了 10 秒 `AbortController` 超时。拿到的清单会回写 `chrome.storage.local.modelConfig`，因此断网时仍有上一版清单可用。
16| 2. **版本号**。`src-mirror/script/service_worker_new.js@9894` 是 `async getVersionConfig()`，从 `chrome.storage.local.moduleVersionConfig` 读版本表；`getFileVersion`（`src-mirror/script/service_worker_new.js@10339`）据此产出查询串：`env==='test'` 时给 `?v=test${Date.now()}`，版本表 `isOpen` 且命中时给 `?v=${version[key]||version.default||'1.0'}`，否则退化为按小时取整的 `?v=${Math.floor(Date.now()/36e5)}`。这条三级降级很关键：热更配置失效时 URL 仍然每小时变一次，不会永久钉死在坏版本上。
17| 3. **模块匹配**。`src-mirror/script/service_worker_new.js@10553` 的 `matchModule(e,r)`：先用 `new URL(e)` 拆出 `hostname` 与 `hostname+port+pathname` 两个串，然后遍历 `modules[]`，只认 `enabled` 且 `patterns` 为数组的项，对每个字符串 pattern 做 `a.includes(r) || t.includes(r)`。**纯子串包含，不是正则**。匹配成功后还要过权限：`checkPermission`（`src-mirror/script/service_worker_new.js@11012`）要求模块的 `permissions` 数组里含当前站点标识，无 `permissions` 或空数组视为全放行。
18| 4. **拉脚本并注入**。`src-mirror/script/service_worker_new.js@15724` 是 `async loadRemoteScripts(tabId, frameId, scripts, versionKey, loadGen=null, options={})`。它对每条 `remoteScripts` 条目做 `@` 拆解：含 `@` 时 `path=split('@')[0]`、`versionKey=split('@')[1]`；随后拼最终 URL，见 `src-mirror/script/service_worker_new.js@16111`：`` `${AppConfig.cdnHost}/${r}${a}` ``（`a` 即 `getFileVersion` 的查询串）。命中 `codeCache` 直接复用并标 `fromCache:true`，未命中才 `fetch` 后 `addToCodeCache`，全部 fetch 用 `Promise.all` 并发。样式走同构的另一条路径：`src-mirror/script/service_worker_new.js@18660` 起是 `loadRemoteStyles`，URL 拼法与脚本完全一致，缓存也共用同一个 `codeCache`。
19| 
20| 最后一道门槛是核心库优先：调用点在 `src-mirror/script/service_worker_new.js@21145`，必须先 `await this.ensureCoreLibrariesReady(...)` 为真，才执行 `loadRemoteScripts(..., {trackCritical:true})`；否则直接打「核心库未就绪（PluginVue 缺失）」并跳过业务脚本 eval。`trackCritical` 的实现见 `src-mirror/script/service_worker_new.js@17762`：只把 `PluginVue is not defined` / `$ is not defined` / `jQuery is not defined` 三类错误认定为关键失败（`hasCriticalFailure`）。换句话说，**上架引擎依赖宿主页面已注入的 Vue 与 jQuery**，缺一个就整体不启动，而不是半启动。
21| 
22| ## 3. 分发结果：17 个模块共用同一份产物，8 个是上架入口
23| 
24| 实测远端清单 `config.json` 共 25 个模块，其中 **17 个**模块的 `remoteScripts` 含 `dist2/goods_manager/js/index.js`，而 `versionKey` 恰为 `goods_m` 的正是**上架相关的 8 个**：`xiaohongshu_publisher`（`ark.xiaohongshu.com`）、`goods_manager`（`item.upload.taobao.com` / `sucai.wangpu.taobao.com` / `sell.publish.tmall.com`）、`kuai_shou_publisher`（`s.kwaixiaodian.com` / `app.kwaixiaodian.com`）、`douyin_publisher`（`fxg.jinritemai.com` / `haohuo.jinritemai.com` / `douyin.com`）、`weidian_publisher`（`store.weixin.qq.com` / `weidian.com`）、`jd_publisher`（`wares-jdm.jd.com`）、`xianyu_publisher`（`goofish.com`）、`1688_publisher`（`offer-new.1688.com` / `work.1688.com`）。其余 9 个（`tb_detail`、`tb_trade`、`1688_detail`、`pdd_sycm`、`pdd_ykd`、`jd_consum`、`dy_detail`、`douyin_detail`、`xhs_detail`）是采集侧模块，也复用同一个包。**8 个平台上架能力，安装包里 0 行代码，CDN 上 1 个 JS 文件**——这就是多平台上架的最小充分结构。

26| ## 4. 跑完之后：三层落库
27| 
28| 上架与采集产物不写 `chrome.storage`，而是走「页面 → Service Worker → IndexedDB」的桥。桥的注册点在 `src-mirror/script/service_worker_new.js@71697`：`case 'indexeddb_set': return await IndexedDBManager.setItem(data)`，同段还有 `indexeddb_get` / `remove` / `clear` / `getAllKeys` / `getStats` / `cleanExpired` / `setMultiple`，即一整套 KV 原语。真正的库在 `src-mirror/script/service_worker_new.js@32062` 的 `class IndexedDBManager`：`DB_NAME='PluginStorage'`（`src-mirror/script/service_worker_new.js@32092`）、`DB_VERSION=1`、`STORE_NAME='keyValueStore'`，`onupgradeneeded` 里建 `keyPath:'key'` 的对象仓并加 `createIndex('expireTime', ...)`（`src-mirror/script/service_worker_new.js@32520`）。`setItem` 写入的条目形如 `{key, value, expireTime: expireMinutes ? Date.now()+60*expireMinutes*1e3 : null, createTime}`——**TTL 是写进记录里的绝对时间戳**，`getItem` 读到过期记录会顺手 `removeItem` 并返回 `data:null`，即惰性淘汰。
29| 
30| 引擎侧的封装是 `scripts/_gm.js@358841` 的 `class a{constructor(){this.storage=n['default'],this.prefixes=...`，前缀表逐个可读：`product:'goods_manager_product_'`（`scripts/_gm.js@358904`）、`publish:'goods_manager_publish_'`（`scripts/_gm.js@358976`）、`history:'goods_manager_history_'`（`scripts/_gm.js@359044`），配套 `defaultExpiry={product:60, collection:30, publish:1440, workflow:10080, history:43200, cache:60}`（单位分钟）。上架结果的写入口是 `scripts/_gm.js@360979` 的 `async savePublishResult(e,t=null)`：键为 `` `${Date.now()}_${e.platform}` `` 再加 `prefixes.publish` 前缀，值里带 `productKey`（回指商品记录）、`savedAt`、`version:'1.0.0'`，并以 `indexeddb_set` + `expireMinutes: this.defaultExpiry.publish` 发出——所以**每条上架记录默认保留 24 小时**，且平台名进了主键，天然按平台可检索；读回侧是 `scripts/_gm.js@361354` 的 `loadPublishResult`。商品侧同理：`scripts/_gm.js@359271` 的 `saveProductData` 会先校验 `e instanceof ProductData`，键取 `e.storageKey` 加 `goods_manager_product_` 前缀。
31| 
32| 第三层是失败兜底。`sendBackgroundMessage` 抛错后先过 `isExtensionContextError`（`scripts/_gm.js@364771`），它靠错误文本匹配 `Extension context invalidated` / `extension context` / `receiving end does not exist` / `could not establish connection` 四类；命中就退到 `saveToLocalStorage`（`scripts/_gm.js@365054`），把 `{value, timestamp, expireTime}` 写成 `localStorage` 的 `backup_${key}`，读取侧 `loadFromLocalStorage`（`scripts/_gm.js@365233`）同样做过期判断。**Service Worker 被回收（MV3 常态）时数据不丢，落进页面 localStorage 的备份键**，这就是上架过程中刷新页面仍能续上的原因。
33| 
34| ## 5. 出错往哪报：分级、去重、批量
35| 
36| 上报器在同一个包里。分级表见 `scripts/_gm.js@353910`：`errorSeverity={CRITICAL:{level:4,shouldReport:!0,maxRetries:5}, HIGH:{level:3,shouldReport:!0,maxRetries:3}, MEDIUM:{level:2,shouldReport:!1,maxRetries:2}, LOW:{level:1,shouldReport:!1,maxRetries:1}}`——**只有 CRITICAL / HIGH 才上报，MEDIUM / LOW 只本地计数**，这是很克制的设计。哪些算 CRITICAL 由 `scripts/_gm.js@354112` 的白名单决定：`TITLE_NOT_FOUND`、`MAIN_IMAGE_NOT_FOUND`、`PLATFORM_DETECTION_FAILED`、`COLLECTOR_INITIALIZATION_FAILED`、`PUBLISHER_INITIALIZATION_FAILED`、`API_COLLECTION_FAILED`、`IMAGE_DOWNLOAD_FAILED`、`STORAGE_SAVE_FAILED`、`VIP_PERMISSION_CHECK_FAILED`。这张表本身就是一份上架链路关键步骤清单：标题、主图、平台识别、采集初始化、发布器初始化、接口采集、图片下载、落库、VIP 校验，缺任一环都算致命。
37| 
38| 入口是 `scripts/_gm.js@354553` 的 `async handleError(e,t={},r='MEDIUM')`：它先 `generateErrorId`（`scripts/_gm.js@356482`，拼成 `${类型}_${operation}_${platform}`）得到稳定 id，再 `incrementErrorCount`（`scripts/_gm.js@356691`）累计同 id 次数作为 `context.attempt`，最后按 `severity.shouldReport && shouldReport(o)` 决定是否真的上报，并把 `attempt <= maxRetries` 作为返回值——调用方据此判断还能不能重试。去重逻辑在 `scripts/_gm.js@356939` 的 `shouldReport(e)`：非 `criticalErrorTypes` 直接 `false`，否则用 `${type}_${platform}_${url}` 作键查 `reportedErrors` 集合，**同一个页面上同一类致命错误只报一次**。重试退避由 `withRetry`（`scripts/_gm.js@355068`）实现：`delay=min(baseDelay*exponentialBase^(n-1), maxDelay)`，再乘 `0.5+0.5*random` 的 jitter。
39| 
40| 真正的网络出口只有两个，都在 `scripts/_gm.js`：单条是 `/plugin/api/error/report`（`scripts/_gm.js@357564`），批量是 `/plugin/api/error/reportBatch`（`scripts/_gm.js@357802`）。批量策略由构造函数里的 `batchSize=10`、`reportInterval=3e4` 决定：`reportError`（`scripts/_gm.js@357135`）把错误 push 进 `reportBatch`，长度到 10 或 `severity==='CRITICAL'` 立即 `flushErrorReports`（`scripts/_gm.js@357319`），否则 `scheduleErrorReport`（`scripts/_gm.js@358055`）起一个 30 秒定时器；`flushErrorReports` 失败时会把整批 `unshift` 回队列，**不丢**。注意上报走的是 `apiHost`（`src-mirror/config/app-config.json:5` 的 `https://p-api.koudai89.com`）下的 `/plugin/api/*`，与上架引擎的 CDN 分发是两条完全独立的通道——**能力热更走 CDN，遥测与业务接口走 apiHost**。

42| ## 6. 链路一图
43| 
44| ```
45| manifest.json（1 个 Service Worker）
46|   └─ ModuleLoaderManager.getConfig()        cdnHost + /config.json?v=ts，10s 超时，回写 storage
47|        └─ matchModule(url)                  patterns 子串包含 + checkPermission
48|             └─ loadRemoteScripts(scripts, versionKey)
49|                  ├─ getFileVersion  -> ?v=  test / 版本表 / 每小时取整 三级降级
50|                  ├─ codeCache(<=50) 命中即复用
51|                  └─ ensureCoreLibrariesReady  否则跳过（PluginVue/$/jQuery 缺失视为关键失败）
52|                       └─ dist2/goods_manager/js/index.js   17 模块共用，8 个是上架入口
53|                            ├─ 落库 IndexedDB(PluginStorage/keyValueStore，expireTime 惰性淘汰)
54|                            │    prefixes: goods_manager_{product,publish,history,...}
55|                            ├─ 兜底 localStorage backup_<key>（SW 被回收时）
56|                            └─ 上报 /plugin/api/error/report(Batch)  仅 CRITICAL/HIGH，去重 + 批量
57| ```
